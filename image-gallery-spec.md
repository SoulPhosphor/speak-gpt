# Image Gallery Specification

**Status:** Owner-approved product/UI design, August 23, 2026.

**Scope:** Generated-image gallery, image persistence/deletion behavior, image-safe chat deletion, and the related drawer/chat actions. This specification extends `drawer-design-spec.md` and `image-generation-rebuild-plan.md` for these areas. It does **not** redesign image generation providers, prompt generation, Playground, Companions, or unrelated chat behavior.

The repository safety, shared-style, theme, lifecycle, and accessibility rules in `CLAUDE.md`, `ui-style-guide.md`, `ui-style-adoption.md`, `drawer-design-spec.md`, and `image-generation-rebuild-plan.md` still apply.

Unless the owner explicitly says otherwise, icons named in this specification come from **Google Icons / Material Symbols**. New labels and control/accessibility names use Title Caps according to `ui-style-guide.md`.

---

## 1. Product Goal

Generated images must remain manageable even after a user has accumulated many chats and many images.

The app needs a first-class **Image Gallery** that:

- shows completed images generated by the app;
- survives deletion of the chat that originally created an image unless the user explicitly chooses to delete the image too;
- lets the user open, save, locate, and deliberately delete images;
- never silently destroys image files merely because a chat was deleted;
- preserves chat history when an image file itself is deliberately deleted;
- remains responsive with a large image collection.

This gallery is for **generated images**. User-uploaded attachments, persistent Includes, Companion/profile images, and other unrelated images are not gallery items unless separately approved later.

1. **Image Gallery**
2. **Playground** while it exists

## 3. Gallery Screen

### 3.1 Header

Use the app's approved full-screen header family. Header title:

**Image Gallery**

Use the current shared header styles rather than inventing a local header appearance.

### 3.2 Gallery Controls

Keep the first version deliberately small. The gallery has compact controls at the top for sort order, column count, and optional labels.

#### Sort

Choices:

- **Newest to Oldest** — default
- **Oldest to Newest**

Sort by the generated image's stored creation time (`createdAt`), not by a filesystem modification timestamp.

#### Columns

Use a compact dropdown containing only these numeric choices:

- **2**
- **3** — default
- **4**

Do not offer 5 columns in the first implementation. **Four is the maximum.** Three-across is the intended default phone density and should use the existing Profile Images gallery's roughly three-across phone presentation as the visual size reference. The generated-image gallery still uses the explicit 2/3/4 user-selected dropdown rather than copying the Profile Images gallery's automatic span-count calculation.

#### Show Labels

Add the compact **Show Labels** control using the same small presentation already approved in the Profile Images gallery:

- plain **Show Labels** text;
- a small `MaterialSwitch` immediately beside it;
- not a tile, card, chip, or full-size settings row;
- tapping the text may toggle the switch, matching the existing Profile Images behavior;
- default: **On**, matching the existing Profile Images Show Labels preference behavior;
- persist the choice app-wide across gallery visits.

When **Show Labels** is On, each gallery cell displays a small two-line label block **above the image**:

1. origin **chat name**;
2. the image's **creation date** underneath it.

Chat-name rules:

- one line only;
- end-ellipsize/truncate when the name does not fit;
- never expand to a second title line;
- use quiet gallery typography so the image remains the dominant element.

Date rules:

- derive it from the generated image's stored `createdAt` value;
- show the date the image was created, using the app's normal locale-aware date formatting rather than a filesystem timestamp;
- place it directly under the chat name using subordinate text styling.

When **Show Labels** is Off, remove the entire label block and reclaim its vertical space; do not leave empty label placeholders above thumbnails.

Persist sort order, column count, and Show Labels app-wide so reopening Image Gallery keeps the user's selected presentation.

Use the canonical shared dropdown/selector system from `ui-style-guide.md` for Sort and Columns. Reuse the Profile Images gallery's compact Show Labels interaction pattern rather than inventing a second toggle presentation.

### 3.3 Grid

- Use a virtualized grid (`RecyclerView`/`GridLayoutManager` or the repository's equivalent established mechanism), not a container that inflates every image at once.
- The selected Columns value directly controls the grid span count: 2, 3, or 4.
- Keep the thumbnail itself visually square/consistent within its column. When labels are enabled, the label block sits above the thumbnail rather than consuming or overlaying part of the image.
- Three columns should be visually comparable in thumbnail size/density to the existing Profile Images gallery's normal three-across phone presentation.
- Load/decode thumbnail-sized representations for visible/nearby cells. Do not decode every full-resolution image simply to populate the gallery.
- Opening the full image is the point where full-resolution content is needed.
- Recycled grid cells must clear stale images, chat-name/date labels, listeners, and visibility state before rebinding.
- Missing/deleted files are not valid gallery thumbnails; a deliberately deleted image leaves the gallery but may remain represented by a placeholder inside chat history as defined in Section 7.

## 4. Short Press: Open Image

Short-pressing a gallery thumbnail opens the image in the app's image viewer.

Reuse/extend the existing `ImageBrowserActivity` behavior where practical rather than building a second full-screen image viewer. The current viewer already supports zooming and Android's choose-where-to-save document flow.

### Save Action

- Put the Google **Download for Offline** / `download_for_offline` icon in the lower-right action area for the save action.
- Accessibility/control name: **Save Image**.
- Tapping it launches Android's document-create flow so the user chooses the destination and filename.
- Reuse the existing `ACTION_CREATE_DOCUMENT` save behavior already used by `ImageBrowserActivity`.

This specification does not require removing any already-approved viewer action such as Share merely because Save is called out here. Do not delete existing viewer functionality as collateral work.

## 5. Long Press: Image Action Menu

Long-pressing a gallery thumbnail opens the app's **compact action popup** with:

1. **Go to Chat**
2. **Delete**

### Compact Popup Style

The gallery image menu and the drawer chat long-press menu (Section 11) use the same compact popup/menu appearance.

The app is standardizing these small action menus. Do not independently style each `PopupMenu`/small anchored menu.

If implementation begins before a named shared compact-popup style/theme exists, add one shared style/theme/behavior pattern and document it in `ui-style-guide.md`, then use it for both menus. Do not solve this with local background/tint/spacing code in individual screens.

### Go to Chat

- Opens the chat in which the image was originally created.
- Use the durable origin chat identity from the gallery catalog, not a chat-name guess.
- When feasible, navigate/scroll to the exact generated image using its stable `imageId` or stored message identity.
- If exact-message positioning is unavailable in the first implementation, opening the correct origin chat is acceptable.
- If the origin chat has been deleted, **Go to Chat** is unavailable (hide or disable it). The image remains usable in the gallery.

### Delete

Delete opens the confirmation in Section 6.

## 6. Delete an Image from the Gallery

Deletion is deliberate and separate from deleting a chat or deleting a chat message.

Show a standard app dialog:

**Title:** `Delete This Image?`

**Actions, exact order:**

1. **Cancel**
2. **Okay**

Use `App.MaterialAlertDialog` and the approved centered cancel-first two-action layout/style. Do not invent another dialog appearance.

If the user confirms:

1. delete the gallery image asset;
2. remove its active gallery-catalog entry;
3. do **not** delete the chat message that originally contained it;
4. do **not** rewrite or erase the historical prompt/summary/metadata solely because the image bytes are gone;
5. any chat message that references the deleted image renders the missing-image placeholder from Section 7.

A deliberate Gallery Delete is stronger than the existing `GeneratedImageFiles.deleteIfUnreferenced(...)` cleanup path. That existing helper is intentionally conservative and refuses to delete a file while another stored chat still references it. Gallery Delete is an explicit owner-approved/user-confirmed file deletion and therefore must have its own deliberate operation rather than weakening the safe cleanup helper globally.

If multiple chats reference the same generated image/file, deliberately deleting that gallery image means those references all become missing-image placeholders. The user explicitly confirmed deletion of the image asset.

## 7. Deleted/Missing Image Placeholder in Chat

Deleting an image file does **not** delete the historical chat message.

Where the generated image used to render, show a simple missing-image placeholder using the Google **X-circle / Cancel** icon.

Requirements:

- Preserve the message's generated-image metadata, prompt, summary, timestamps, and other historical information.
- The placeholder must not be mistaken for a generation failure/retry state; it specifically means the previously generated image asset is no longer available.
- Do not silently remove the entire message because its file is gone.
- Do not crash when a legacy or current generated-image message references a missing file.
- Accessibility text should identify the state, e.g. **Image No Longer Available**.

This placeholder also covers another chat that referenced the same image after the asset was deliberately deleted.

## 8. Durable Gallery Catalog / Ownership

The gallery cannot be derived only from currently-existing chat messages, because the approved product behavior allows an image to remain after its origin chat is deleted.

Create a lightweight, durable generated-image catalog/index independent of chat existence.

At minimum each completed gallery image needs durable identity/linkage sufficient for:

- stable `imageId`;
- stored file hash/path identity;
- MIME type and dimensions where already known;
- `createdAt`;
- **origin chat ID**;
- **origin/last-known chat name** for the optional gallery label;
- origin message/image identity when available, so **Go to Chat** can locate it precisely;
- enough existing generated-image metadata to render/manage the gallery without opening every full chat history.

The existing `GeneratedImageMetadata` stored with a message remains valid conversation provenance; do not replace it with a gallery-only record. The catalog is an index/ownership layer so gallery existence is not hostage to chat existence.

### Gallery Chat-Name Label

The gallery needs a durable display name even when its origin chat is later deleted.

- While the origin chat exists, keep the gallery catalog's stored chat name synchronized with normal chat renames so Show Labels reflects the current name.
- If the origin chat is deleted while the image is kept, retain the **last-known chat name** in the gallery catalog for display.
- Do not replace a deleted chat's retained name with a generic current-chat name or another guessed value.

### Ownership Rule

For deletion-with-chat decisions, an image belongs to the chat in which it was **originally created**, not every chat that happens to reference/copy the same file.

This distinction matters because copied/duplicated chats can legitimately share a generated-image file hash. Deleting a copied chat must not accidentally claim ownership of and delete an image originally created elsewhere.

### Existing/Legacy Images

When introducing the catalog, backfill existing completed generated images conservatively from stored chat metadata/history.

- Prefer existing stable `imageId`, `fileHash`, and `createdAt` values.
- Capture the source chat's name as the gallery label when that source can be established safely.
- Do not manufacture origin ownership or a chat-name label from the currently-open chat or another unrelated setting.
- Skip files that do not actually exist rather than resurrecting intentionally deleted assets into the gallery.
- If legacy data cannot establish an origin safely, keep the image accessible where possible but do not guess destructive ownership.

## 9. Image Generation Setting: Delete Images with Chat?

Add a toggle at the bottom of the existing **Image Generation** settings screen:

**Delete Images with Chat?**

Default: **Off**.

This is an app-wide setting, consistent with the rest of the rebuilt Image Generation settings.

Important semantic rule: **On does not silently delete image files when a chat is deleted.** On enables the explicit image-deletion choice in the chat-delete confirmation described in Section 10. The user must still choose **Delete All** for image files to be destroyed.

Provide short explanatory text so the setting cannot be mistaken for an unconfirmed automatic purge, e.g.:

`When deleting a chat, choose whether to keep or delete images created in it.`

Use the existing shared toggle-row style. Do not hard-code this control into a unique local appearance.

## 10. Chat Deletion and Generated Images

There is already a centralized `ChatDeleteDialog`. Extend/route deletion through shared behavior rather than cloning image-deletion rules at each call site.

The delete experience depends on the setting and whether the chat actually owns any generated images.

### 10.1 Delete Images with Chat? = Off

This is the default and safest behavior.

If the chat owns generated images, retain the existing delete-chat confirmation and add explanatory text:

`Images created in this chat will still be available in the Image Gallery.`

Keep the existing approved delete-chat actions unless another current product spec has already changed them.

If the chat owns **no** generated images, no image-specific message is necessary. Keep the ordinary delete-chat confirmation uncluttered.

Deleting the chat removes the chat but leaves its gallery images and catalog entries intact. Their origin-chat link becomes unavailable, so **Go to Chat** is no longer offered for those gallery items. The catalog retains the last-known chat name for Show Labels.

### 10.2 Delete Images with Chat? = On

If the chat owns one or more generated images, show the explicit three-choice confirmation.

Include the warning text:

`Any images created in this chat will be deleted also.`

**Actions, exact order:**

1. **Cancel**
2. **Delete Chat Only**
3. **Delete All**

Semantics:

- **Cancel** — do nothing.
- **Delete Chat Only** — delete the chat and preserve its images in Image Gallery.
- **Delete All** — delete the chat **and the image assets originally created by that chat**.

`Delete All` does not mean every image referenced by the chat. Use the origin-ownership rule in Section 8.

If another chat references an image explicitly deleted by **Delete All**, that other chat keeps its historical message but renders the Section 7 missing-image placeholder.

If the chat owns **no** generated images, do not show a pointless three-action dialog. Use the ordinary chat-delete confirmation.

### 10.3 Three-Action Dialog Layout

The existing shared dialog layouts are primarily one- and two-action layouts. Do **not** squeeze the three long labels into a cramped horizontal row simply to reuse a two-button scaffold.

Add an appropriate **shared three-action dialog layout/variant** if one does not exist when implementation begins. It may stack/adapt the buttons so the exact labels remain readable while preserving this action order. Document that shared variant in `ui-style-guide.md`.

Use the app's existing semantic button families; do not invent local colors or shapes for this dialog.

### 10.4 Every Chat-Deletion Entry Point Must Obey This Policy

The image policy is not only for the drawer.

At implementation time, audit the currently reachable deletion entry points and route them through one shared deletion decision/coordinator. This includes at least:

- current-chat overflow Delete;
- drawer long-press Delete;
- the legacy Chats screen while it remains reachable during drawer migration;
- swipe/bulk delete paths that remain active during migration;
- any other direct `ChatPreferences.deleteChat(...)` UI path.

No old swipe or bulk path may silently bypass the new image-preservation warning/choice.

Do not weaken the low-level storage method to show UI; centralize the UI/policy above it so non-UI storage code remains deterministic.

## 12. Current Chat Overflow: Pin / Unpin

In the current chat's top-right vertical three-dot overflow menu, add a dynamic item at the **top**:

- **Pin** when the current saved chat is not pinned.
- **Unpin** when the current saved chat is pinned.

Requirements:

- Use the existing persisted pin state and the same pin/unpin behavior as the drawer.
- Do not create a second independent pin system.
- If the current view is the blank/unsaved startup chat and there is no durable chat ID to pin, omit Pin/Unpin rather than creating an implicit saved chat just because the menu opened.
- Preserve the current Logs/Delete and other existing overflow behavior below the new Pin/Unpin entry.
- Updating pin state must be reflected in the drawer the next time its list refreshes/opens.

## 13. Performance and Loading

The gallery must be designed for collections larger than the current one.

- Build from the lightweight gallery catalog rather than scanning/parsing every full conversation each time Image Gallery opens.
- Grid cells use thumbnail-sized image loads.
- Full-resolution decode belongs to the viewer, not every grid bind.
- File/catalog reads and deletion work that may block belong off the main thread.
- Sorting and displayed dates use catalog `createdAt` metadata.
- Chat-name labels use lightweight catalog metadata rather than opening full chat histories during grid binding.
- Do not make a missing/deleted origin chat block gallery startup.
- RecyclerView recycling must not display the wrong thumbnail, chat name, date, or Show Labels visibility after fast scrolling.

A visible paging/Load More control is not required for the first version. If future scale requires storage-level paging, preserve global sort correctness and do not make older images disappear from the user's conceptual gallery merely because they are not currently loaded.

## 14. Style and Theme Requirements

- New Gallery UI uses shared styles/theme attributes. No hard-coded gallery palette.
- Use `Widget.App.ActionBar*`, canonical dropdowns/selectors, shared typography, shared row/toggle styles, and the standard dialog theme where appropriate.
- The gallery's compact Show Labels control should reuse the existing Profile Images plain-label-plus-switch visual pattern rather than becoming a full settings row.
- The gallery grid may need a local layout because it is feature-specific; its colors, spacing roles, text appearances, label typography, and controls still belong to shared/theme-ready resources where repeated/changeable.
- The two compact action menus (gallery image and drawer chat) must share one compact menu appearance.
- Any new shared three-action dialog layout and compact popup-menu style must be documented in `ui-style-guide.md` when implemented.
- All visible control names, dialog titles, menu items, and accessibility labels follow Title Caps; explanatory sentences remain sentence case.

## 15. Implementation Safety / Tests

At minimum cover:

1. Gallery defaults to **Newest to Oldest**, **3 columns**, and **Show Labels On**.
2. User can switch the Columns dropdown among **2 / 3 / 4**, 4 is the maximum, and the choice persists.
3. Three-column default thumbnail sizing is visually comparable to the existing Profile Images gallery's normal three-across phone presentation.
4. Show Labels uses the compact plain-text + switch presentation and persists app-wide.
5. Show Labels On renders the one-line origin chat name above each image with the localized creation date beneath it.
6. Long chat names truncate/ellipsize to one line and never increase the label block to a second title line.
7. Show Labels Off removes both chat name and date and reclaims their vertical space.
8. Chat rename updates the catalog/display name; keeping an image after chat deletion retains the last-known chat name.
9. Oldest/Newest sorting uses `createdAt` deterministically.
10. Short press opens the correct image; Save launches choose-destination behavior.
11. Long press shows **Go to Chat** + **Delete** in the shared compact menu.
12. Go to Chat opens the correct origin chat when it still exists and is unavailable when that chat is gone.
13. Gallery Delete requires `Delete This Image?` confirmation.
14. Gallery Delete removes the asset/catalog item without deleting the historical chat message.
15. A chat referencing a deleted image renders the X-circle placeholder and does not crash.
16. The placeholder does not erase stored prompt/summary/provenance metadata.
17. `Delete Images with Chat?` defaults Off and persists app-wide.
18. Setting Off + chat with images warns that images remain in Image Gallery.
19. Setting Off + chat without images does not add pointless image warning text.
20. Setting On + chat with images offers **Cancel / Delete Chat Only / Delete All** in that exact order.
21. **Delete Chat Only** keeps gallery images.
22. **Delete All** removes only images owned/originated by that chat, not unrelated/shared references merely present in the chat.
23. Another chat referencing a deliberately deleted shared asset gets the placeholder rather than a crash or silent message deletion.
24. Copied/duplicated chats do not gain destructive ownership of images created by the original chat.
25. Legacy catalog backfill does not guess ownership from current settings/current chat and skips missing files.
26. Every reachable chat deletion UI path observes the same image policy; old swipe/bulk paths cannot bypass it.
27. Drawer long press shows dynamic Pin/Unpin + Delete.
28. Current-chat overflow shows Pin/Unpin at the top only for a saved chat.
29. Pin state stays consistent between overflow, drawer, and persisted chat list.
30. Grid scrolling/recycling never leaks one image thumbnail, chat-name/date label, or Show Labels state into another cell.
31. Gallery opening and chat deletion do not block the UI thread on full-history scans or full-resolution image decoding.
