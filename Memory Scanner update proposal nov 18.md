# Memory Scanner update proposal nov 18

**Design proposal for review · November 18, 2026 · Associative Memory Scanner and Memory Browser**

Use the original eligible messages as the source for extraction, with the editable Associative Memory prompt and per-chat Analysis Note guiding what to keep. Let the scanner revise its own temporary drafts as it reads. Use the on-device embedding model to find related memories and show the user why two records were brought together. Keep a straightforward short scan to one generative request whenever possible.

## Implementation order

The [memory roadmap, M.2](conversation_recall_plan.md#m2-the-build-order) schedules this proposal after completed Stage 6 and before Stage 7. Assign one lettered stage at a time.

| Stage | Deliverable |
|---|---|
| **6A — Reliable reading and resume** | Current-source and visibility checks, short and long request paths, excerpts, turn references, oversized-turn retry, and interruption recovery through existing scan controls. |
| **6B — Draft corrections and memory matching** | Working-draft edits, local lookup, linked candidates and conflicts, conditional review, cap handling, and revalidation at filing. |
| **6C — Browser match cards and comparison** | Show matches and their status, open the exact pair, read both records, and return to the same list position. |
| **6D — Browser review actions and end-to-end evaluation** | Resolve Pending pairs and conflicts safely, then evaluate the complete scan-to-review experience. |

6A can start with the current Browser. 6B defines the data the Browser consumes. Ship workflows needing new human decisions with their corresponding actions in 6D. Wider Browser redesign work can be scoped separately.

## What happens today

On `main` at `a3c0751`, the scanner reads a frozen range of eligible transcript rows. A normal chat scan starts after its bookmark. Before each extraction request it can already search **active memories** using embeddings, with keyword fallback. Each chunk sees a bounded selection of earlier proposals (up to ten within a text budget). The model can write a correction, but the collector combines exact repeats and otherwise keeps proposals in arrival order. The first eligible proposals can fill the user's limit before a later correction is filed.

Embedding support also exists in the Browser's Possible Match review. The current finder scores comparable active memories and can compare archived or superseded records on demand. It returns match identities and categories to the UI. The exact-duplicate check covers pending drafts too. Differently worded **pending** drafts and **temporary drafts from this scan** are the gap in semantic comparison. A user who scans several chats before reviewing can accumulate the same suggestion several times.

## Check the current source before reading

Stage 6A must check captured transcript rows against the current chat. Capture occurs when a reply finishes. A captured copy alone cannot establish that its wording, visibility or reply version is still eligible.

Resolve each source turn by stable chat and message ID. Before each section, retry and resume, check that the message exists, is visible to the AI, is finished, belongs to the canonical reply version used in requests, and has the expected model-facing text fingerprint. Browsing an alternative reply does not change the canonical version. Read the current eligible wording. Rebuild fragments and offsets when that wording changes.

Record hide and other source changes even while a row is claimed. Today, `MemoryStore.setTranscriptMessageHidden()` filters on `processed_at IS NULL AND claim_run_id IS NULL`, so a hide can be lost during a running scan. A claim reserves work and must not prevent recording the user's change.

If an already-read source changes, invalidate dependent excerpts, carried transcript prefixes, draft edits and suppression decisions. Restart that conversation's unfinished scan from its bookmark against current eligible source, as the memory development plan's Stage 6A requirements specify. Recheck source versions before publishing, including changes made while an API request was in flight. Do model work outside the save transaction and verify those versions at commit. An outdated response cannot publish a memory from a hidden, deleted or replaced reply.

Freeze the selected range's membership and bookmark boundary for recovery, while checking the current eligibility and text within that range. New messages belong to a later scan. An invalidated fragment must not be treated as successfully read merely because its old offset was checkpointed. These checks apply to Rerun too.

For legacy captured turns without message IDs, resolve a source only when existing chat, role, text and available position/date evidence identify it unambiguously. Repeated text alone cannot identify a turn. Skip an unresolved legacy source and report the incomplete coverage through the existing scan outcome. Never guess a current message or send a stale copy. Do not advance a success bookmark across unresolved eligible source. An unresolved legacy source must not block the chat permanently; the memory development plan's Stage 6A requirements govern the outcome.

Use original eligible messages for scanner extraction. Compaction and Summary Section prompts serve other purposes and supply no scanner context in this implementation.

## Read in order, with two paths

| Situation | Proposed behavior |
|---|---|
| The eligible text fits in one request | Send it once. Let the scanner see the outcome before writing its proposals. Allow room for instructions, retrieved memory context, and the response. |
| Multiple requests are needed | Send sections chronologically. Clearly mark the new section. Carry earlier transcript text forward within a bounded allowance when it helps interpretation, along with eligible working drafts. Reserve space for the new source and response first. Send all eligible working drafts while they fit, then select by relevance when necessary. Each request can add a draft, correct one, or withdraw one. |
| Earlier text and drafts outgrow the request | Keep all eligible text in sequence across the scan. For each request, select relevant earlier drafts locally and bring back short excerpts from **this scan** where needed. Include the relevant part of the preceding dialogue for replies such as “she finally did.” An older draft can return after a long change of subject. |

Use the estimated size of the transcript being scanned and the **selected scanner model’s** request settings. A chat’s cumulative usage can count the same input many times. Honor the existing average and maximum settings, scene boundaries, output allowance, and context-limit retry. Where the endpoint has a context window recorded for this model, use it. Otherwise start from the configured chunk sizes. For a long scan, retain earlier source text where its value justifies the input cost. When selecting optional excerpts, start evaluation at **256 estimated tokens per passage and 768 total per request**, including preceding dialogue. Slice around the relevant words within the token allowance. Prefer paragraph boundaries, then line boundaries, then spaces between words. Split between Unicode-safe characters only when necessary. Periods are unreliable in dictated text and do not determine boundaries. Reduce this allowance when the request is tight. Every eligible unread passage still gets processed, however long it is.

**Request order and caching.** Put fixed extraction instructions and schema first. Follow with consistently serialized original transcript segments in order. Give each visible turn a stable scan-local reference derived from its frozen row and turn position. Identify a fragment by its offsets in that original turn, including after a retry. In the changing tail, specify the exact newly eligible range, scene, target catalog, retrieved memories, working drafts, and optional excerpts. The same earlier text can then keep the same bytes as it becomes read-only context. Delimit data separately from instructions. A provider may reuse the shared prefix while it fits. Measure actual cache hits and charges before choosing how much history to repeat.

**Oversized-turn retry.** The current retry in `Archivist.kt` lowers the chunk target but passes the original single-message maximum back to the chunker. Plan a fix in the caller and `ArchivistRequestBudget.kt`: after a confirmed size rejection, recompute the available source budget and lower the effective single-message maximum too. Prefer paragraph boundaries, then line boundaries, then spaces between words. If a word exceeds actual provider capacity, split between Unicode-safe characters, carrying the turn reference, role, and offsets into each fragment. Apply these rules to scanner splitting without changing the compaction feature. Every retry must make progress, and the fragments together must cover all unread text. Retain bounded failure handling if the request overhead alone cannot fit.

## How the AI edits drafts

Kotlin owns the temporary collection and issues short IDs. The model returns new proposals plus just the edits it needs. For example, when a later message confirms a reply, it can replace draft 4 with wording that records the reply and preserves an important delay. A replacement may name two drafts when the evidence supports combining them. An omitted draft keeps its text. Explicit withdrawal covers a mistaken draft with nothing worth retaining. Kotlin validates each operation against the draft IDs exposed in that request. Stage independent valid operations once. An invalid withdrawal leaves earlier drafts untouched. For a locally invalid edit or conflicting edits to the same draft, isolate the affected operations and narrowly repair an unresolved correction if necessary. Reserve whole-response repair for an unreadable response. A text correction preserves the original scope and resolved target IDs. An explicit update to the same real-life event can revise an earlier draft across a companion or project change. Changes of placement require a separate decision.

Keep small, scan-local references to the supporting passages so an ambiguous correction can be checked against the speaker’s actual words. Carry the chat’s recorded outer turn role and available row start date on fragments. A user turn may contain somebody else’s email or dialogue spoken by fictional characters. Attribute a statement only when the passage establishes who said it, and distinguish the row date from the date of the event. These passage references are temporary scanner data. A later message can also describe an earlier event, speculate, or report a second reply. Message order alone cannot establish which fact supersedes which. Keep the editable Associative Memory prompt and per-chat Analysis Note in charge of what is worth retaining and how it reads. Suggested default guidance is to *keep the decisions, reasons, details, and outcomes that will matter later. When the situation changed, preserve meaningful history and make the latest supported status clear.*

Only temporary drafts participate in these automatic edits. Genuine updates involving filed Active, Pending, or Archived memories go to user review. The user decides whether to change or reactivate a filed memory. Keep model-rule proposals on their own filing path and Lorebook extraction on its own contract.

## Where embeddings fit after the change

1. **Before extraction**, search comparable **Active, Pending, and Archived** memory records locally, plus eligible temporary drafts on later chunks. The embedding model can compare against Archived even when the writing AI’s prompt is full. Split long query text into overlapping passages that cover the visible source through the end of the turn. Fit each passage to the selected embedding model’s actual query-token allowance after its prefix and special tokens. The current Gemma configurations allow 512 tokens for a query and 2,048 for stored text. Reuse each passage’s query vector across the eligible record sets, union results by record ID, and label each filed match with its status. Within the existing prompt budget, give priority to directly relevant Active and Pending context and include strong Archived matches where space permits. An archived match omitted here remains eligible for comparison after extraction. Reuse the live-chat sectioning logic where suitable, while preserving coverage of the end of a long scanner turn.

   Determine lookup eligibility by scope and eligible targets. Include every Type and No Type in both embedding and keyword searches before and after extraction. A suggested Type is filing metadata and can vary between scans. Across ordinary companion or project changes, earlier same-scan `real_life` drafts about the user’s life and applicable `global` conduct preferences remain discoverable. Keep targeted companion, project, world, campaign, and character records within their eligible placements. Retrieval must surface the older draft ID for a later correction to reach it.
2. **After extraction**, use each proposed memory’s own text to look up comparable Active, Pending, and Archived memories across chats, plus drafts from the current scan. This gives a specific proposed fact a second chance to find a match missed by the broader passage or omitted from the prompt. Search memory records locally. Other chats’ transcripts are unnecessary. Reuse compatible active vectors. Compute missing Pending or temporary vectors on demand and reuse them while valid. For Archived, reuse compatible comparison vectors and compute missing vectors on demand. Keep archive comparisons out of the normal chat index. Refresh them when the represented text or embedding model changes. Keep this scanner comparison separate from what is eligible for injection into a normal chat.
3. **Decide whether there is anything new to file.** If the source adds no information and the fact is already fully represented in the same scope with the same target IDs, suppress the scanner’s extra proposal even when its suggested Type differs or is blank. Preserve the existing record and its Type. Apply this rule to scanner-generated retellings before filing. Manual filing, import, and deliberate user classifications keep their existing rules. Similar wording, overlapping targets, or a high embedding score alone is insufficient for suppression. A passing reference to history already represented in Archived yields no new card. A genuinely new detail about the past, a correction, or an explicit return to a former situation warrants a linked Pending suggestion. Apply this rule when writing and when a plausible match first surfaces after extraction. For the latter, batch unresolved comparisons with just the relevant proposals, matched records, and supporting wording. Use similarity to find the pair and the evidence to decide what changed. A match between two temporary drafts can be resolved within the scan. Preserve the existing exact-wording hash for discarded suggestions. A semantically similar correction remains eligible.
   **When the proposed placement differs**, compare only records already eligible in the current context. Ask what the source adds about the proposed companion, project, or other target. For example, telling two companions about the same former job adds nothing to an existing real-life memory merely because the listener changed. Explicitly asking one companion to remember a job-related preference, or describing something specific to that relationship, can justify a separately placed, linked suggestion. Preserve the existing placement. If the evidence leaves the distinction unresolved, send the candidate and eligible match to review. Existing companion, project, and fictional-world visibility rules still govern every lookup and link.

4. **Without an embedding model**, continue with exact checks, bounded keyword lookup, and validated scanner relationship hints. Label how a match was found. A keyword match has no embedding similarity score. The fallback should also work when only some vectors are ready.

### Bound embedding work and reuse vectors

Route every scanner query window and record embedding through Step 1's single embedding queue at background priority. Live sends go ahead of waiting scanner work and can interrupt a running background read where the model supports cancellation. Checkpoints must distinguish a deferred comparison from a completed one.

Reuse active vectors and reuse Pending, Archived and temporary-draft comparison vectors by record identity, represented-text fingerprint and embedding model tag. Keep scan-local reuse across sections and recovery. The proposed durable design is a separate scanner comparison cache in the encrypted database for filed records, with deletion tied to the memory, invalidation on text or model changes, and bounded eviction so the cache can be rebuilt. Keep it outside the active chat retrieval index. This storage change must be included in the Stage 6B design approval before its migration is implemented. Avoid requiring a full archive embedding pass before the first useful scan result.

Filter scope and target eligibility first. Bound query windows per processing batch, missing-vector generation and comparisons per proposal, then cap the prompt's returned matches. Process longer source coverage in subsequent batches instead of dropping the end of a turn. Calibrate and record explicit starting limits in 6B from measurements, with incremental vector preparation and bounded keyword fallback while vectors are missing. Track unexamined records so fallback never claims an exhaustive semantic duplicate check. Archived remains eligible in both lookup stages. A result cap alone does not bound the cost of generating every missing vector.

Stage 6D measures cold-cache and warm-cache scans on the owner's phone, including a large archive, live-chat contention, total elapsed time, queue waits, vector reads, cache reuse and battery consumption. Build-machine and emulator timings cannot establish the phone budget.

## Memory Browser changes

- On a pending card, show a preview of the closest related memory, its status (Active, Pending, or Archived), and its similarity score when available. Tapping the match should open the **specific pair** by memory ID. Make additional matches accessible from the same card.
- In Possible Match review, show the full proposed and matched wording together, clearly labeled. Present the score as similarity, such as **0.91 similarity**. It measures closeness in wording or meaning and can be high for opposite claims. Distinguish exact matches, keyword matches, and scanner-suggested relationships. Carry actual scores through the match result so the card can display them.
- Reuse the existing review actions where they fit. For two pending drafts, let the user keep both or keep/edit the better version and discard the redundant proposal without activating either by accident. Recheck IDs, status, and match data after an edit or deletion. Returning from comparison should preserve the user’s place in the review list.
- These changes cover the scanner-to-review workflow. A broader Browser redesign deserves its own proposal. Exact labels and layout remain design choices.

## When to spend another scanner request

Finish directly when there are no unresolved draft conflicts or filed-record comparisons and the eligible set fits the user’s suggestion limit. For unresolved conflicts, send the competing drafts and brief supporting excerpts. If the cap is exceeded, rank distinct proposals across the full scanned range for usefulness and topic coverage before filing. Apply the cap to valid, eligible proposals, allowing the next one through when a duplicate or rejection drops out. Preserve the existing behavior for an unlimited setting and for an accepted memory that must split into parts. Budget the final request too: if necessary, resolve small groups first and rank compact references across groups. Never truncate the final list by arrival order.

For multi-request scans, extend the existing encrypted staging data into a resume checkpoint. After each successful section, save the validated working collection with its stable draft IDs, the exact next unread turn and offset, and the current phase in one transaction. On recovery, verify the current source and scan configuration before resuming. Use the source-check rules above to restart the affected remainder when needed. A request interrupted before its result was saved may need repeating. Respect explicit cancellation and never publish unfinished drafts.

If the scan read the full eligible range and bounded repair still cannot reconcile an individual edit, keep the valid work. Retain the original draft. If the new wording independently passes normal candidate validation and is supported by the source, stage it as a separate alternative. Carry a validated link between known counterparts into Possible Match review so the user sees the disagreement before approval. A fabricated target ID cannot establish that link. An invalid withdrawal with no new text yields no second draft. Report the unresolved or skipped edit in the scan outcome. If the cap would separate a linked pair, present both wordings together as one review choice within the cap.

This fallback applies to individual model edits after successful extraction. An unreadable extraction response with exhausted repair, a provider interruption that leaves a section unread, or a failed save still uses the incomplete-scan recovery path. Before filing, revalidate decisions that depended on a filed memory. For an explicit “already covered” decision, keep a small scan-local reference to the supporting passage and the matched record’s identity and version (or fingerprint of the fields used). Use the same checkpoint for resumed runs. This lets the app revisit a changed dependency even when the model returned no draft text for that retelling.

- If a link target disappeared or is now ineligible, drop the link. Keep an independently valid new development as an ordinary proposal if it still passes current duplicate and rejection checks.
- If a suppression still has an eligible record that covers the fact, keep it. If the wording, placement, or status changed enough to affect the decision, reconsider just the affected passage against eligible records. Pending becoming Active can usually be resolved locally.
- If the user discarded the specific Pending wording that accounted for a pure retelling during this scan, honor that action for the already-resolved occurrence. Confirm the discard from the observed record/action or its exact wording hash. A missing ID alone does not establish a discard. The durable rejection rule stays exact-wording only. A correction or new development remains eligible.
- Perform any model comparison outside the database transaction. At commit, verify the affected records still match the checked versions, reapply filing rules, and atomically save proposals and advance the bookmark. If a dependency changed again, recheck the affected decision before committing. Clear the checkpoint after success. Keep a previously completed range complete. The suggestion limit applies to this run’s filed proposals. Rerun can revisit the original source range.

## Quick evaluation for a future implementation

Compare the current scanner and the proposal using the same scanner model, settings, and synthetic conversations. Include a short chat, an approximately 80-message multi-topic chat with a late correction, the same correction buried in the middle, and three chats scanned before any drafts are approved. In the three-chat case, repeat the first event in different words and then introduce a genuinely different decision. Expect one proposal for the original event, no redundant suggestion for merely retelling it, and a linked update for the new decision. Repeat with embeddings unavailable and with a suggestion cap below the number of distinct candidates.

Include a long-turn case in which a companion changes, several topics intervene, and the update appears near the end of a turn longer than the embedding query limit. Expect one accurate pending memory for the evolving event. Also exercise an oversized turn without reliable punctuation rejected by the provider, valid additions alongside an invalid withdrawal, and a pasted email followed by a user correction. Verify complete source coverage, preservation of valid edits, and attribution in the resulting prose. Repeat a fact in the same placement under a different suggested Type and under No Type. Expect zero extra cards and the original classification intact. Add a real change under a different Type and expect a linked update. Exhaust repair on a known pair of conflicting valid drafts and verify both wordings reach review, including at a cap of one. An invalid reference alone must never create a link or a new draft.

Also compare a passing mention of an archived past event with a genuinely new detail about that same event and with a return to the former situation. Expect zero new cards for the retelling and a linked suggestion for each genuine change, including when the Archived match first surfaces after extraction. Interrupt a multi-section scan after a checkpoint and verify that the next run continues at the exact unread position without duplicating earlier edits.

Scan the same real-life fact with two different companions, then add a genuinely companion-specific instruction. Expect no repeat for the changed listener and a separately placed proposal for the instruction. During a paused scan, approve, edit, discard, or remove a matched Pending record. Check both a suppressed retelling and a genuine update for lost facts, stale links, and accidental refiling.

Add source-mutation cases before implementation. Regenerate a reply before scanning, edit a captured message before scanning, delete or hide a message during a request, and repeat those changes while paused. Expect only current visible canonical wording to support filed proposals, invalidated drafts to be rebuilt, and correct resume offsets. Browsing another reply without making it current must leave the canonical source intact. Include an ambiguous legacy turn and verify that it cannot become a falsely successful scan.

Judge the actual prose, chronology, topic coverage, missed or wrongly merged facts, and effort to review on a phone. Compare request count, input/output tokens, cached tokens and cost where reported, elapsed time, and local embedding work. Record the fraction of scans that needed an extra comparison request because the first useful match surfaced only after extraction, separately from cap ranking and edit repair. If frequent, inspect pre-extraction retrieval coverage and prompt limits before increasing request budgets. The first review question is whether ongoing edits plus local matching catch stale and repeated memories economically enough to make a full second transcript read unnecessary.
